# FormFill 开发复盘与可复用验证方法论

> **状态说明（2026-11-18）：** FormFill 已停止产品化并冻结。本文不复盘“如何继续做完这个通用插件”，而是总结从想法、调研、开发、验证到主动停止的全过程，提炼可迁移到下一个小产品或业务想法的决策方法。事实边界以仓库源码、测试、调研文档与 `docs/execution/` 中的证据为准。

## 0. 一句话结论

这次做出了一个可运行、可测试的技术样机，并把下面三个商业问题写成了可执行的验证框架：

1. **这个任务是否真实、重复，而且足够痛？**
2. **现有替代方案为什么不够，用户愿意为余下的价值做什么？**
3. **我们是否能比现有入口更可靠、更便宜或更容易触达地交付，并形成持续付费理由？**

但该框架并未在 FormFill 的真实用户和市场中完整运行：G1–G4 没有执行，真实用户行为、真实任务对照、重复使用和付费仍未验证。FormFill 通过了相当一部分“能不能做”的技术验证，却没有取得“为什么由这个产品持续做、谁持续付费”的商业证据。能够识别这一差别并在继续扩功能前停下，是本次项目最有价值的决策能力。

## 1. 你在项目中实际完成了哪些工作

这里的“你做了哪些工作”指你作为产品负责人实际推动的判断、取舍和验证，而不是把所有代码提交都归到你个人名下。

| 阶段 | 你实际完成的工作 | 产生的资产 |
|---|---|---|
| 产品定义 | 把“AI 自动填表”从一个泛化想法拆成描述/文件输入、字段识别、预览、应用、撤销、Excel 记录与映射复用等可验证能力；要求竞品有的基础功能不能被轻易遗漏 | 功能清单、基础能力基线、F/W/S/M 系列任务编号 |
| 研究设计 | 不满足于参看产品首页，要求全面查看竞品网站、商店规模、网络流量/排名、社交与论坛关注度，并研究 Reddit、Hacker News 等发布文章 | 竞品、营销规模、社区发布、SEO、流量和关键词研究包 |
| 用户假设验证 | 提出老网站、跨境、招投标等方向，并要求反向验证，而不是直接按直觉开发 | 用户画像、场景白名单/黑名单、产品原点报告 |
| 技术深化 | 通过真实模型接口和真实浏览器环境推进验证；要求单记录 Excel、预览确认、撤销、映射复用、隐私停止采集等基础能力 | 可运行 MV3 扩展、130 项测试记录、Playwright 浏览器 E2E、演示包（历史证据记录于 2026-11-17） |
| 产品可信度 | 要求官网不提供假商店按钮、不虚构域名或流量，明确 BYOK、权限、模型外发、限制和未验证事实 | 四页静态网站、预渲染、SEO 准备、隐私政策、商店草案 |
| 质量机制 | 要求逐项审查、测试、记录、提交和推送；要求让 Qwen 独立检查结论并处理分歧 | 多轮 Qwen 审查、执行台账、提交链、可复现证据 |
| 产品决策 | 在看到“开发难度低、平台/客户可自研、替代入口多、尚无付费证据”后，没有继续用功能数量为项目续命，而是主动停止产品化 | 冻结决定、收尾报告、交接边界、重启门槛 |

### 已经验证的

以下扩展能力均为冻结前的历史证据；本次收尾没有重新运行扩展测试，只重跑了网站的静态布局与 axe 检查。

- 核心填写链路在本地测试、真实模型代码级 E2E 和 Playwright Chromium 的真实 MV3 全链路中都跑通过。
- Excel 单记录、预览/应用/撤销、页面变化拒写、已有值保护、结构映射复用等能力具有代码与证据。
- **冻结前网站证据：** 网站四页完成本地构建、预渲染，并有历史响应式与可访问性检查记录。
- **本轮网站静态检查：** 含共享归档横幅的布局 36/36 与 axe 4/4 通过。
- 隐私采集路径被关闭，数据外发和 Key 本地存储边界有文档和测试。
- 项目可以构建、可以复现、可以交接。

### 没有验证的

- 真实用户是否高频完成同一类任务。
- 工具相对手工、平台导入、主体库、OCR、RPA 或专用客户端的稳定增量价值。
- 用户是否愿意为通用插件持续付费。
- 有效获客渠道、转化率、留存和复购。
- 线上 SEO、搜索量和自然流量表现。

**这份边界非常重要：工程完成不等于产品成立，功能存在不等于市场需要，公开关注也不等于使用或付费。**

## 2. 这次做对了什么

### 2.1 把直觉变成了可证伪假设

你没有简单接受“填表工具应该有人用”或“老网站一定适合”，而是把想法拆成：

- 谁在什么场景重复做这件事？
- 目标网站是否有导入/API/ERP 等原生替代？
- 剩余字段是否足够多，人工复核是否真的更快？
- 用户能否接受 BYOK、数据外发与人工确认？
- 是否愿意为一次性适配或持续使用付费？

这让讨论从“我觉得有价值”转向“什么证据会推翻这个判断”。

### 2.2 先跑真实链路，而不是只做静态 Mock

项目最终形成了逐级证据：

1. 单元与集成测试。
2. JSDOM + 真实模型 E2E。
3. Playwright Chromium 加载真实 MV3 扩展。
4. 真实弹窗 UI 完成配置、文件导入、预览、应用、撤销和映射复用。

这个过程还发现了合成测试发现不了的真实缺陷。例如浏览器 i18n key 不合法会导致扩展整个加载失败，下拉占位项会被误判为已有值。这是“真实运行优先于演示稿”的具体收益。

### 2.3 将隐私、安全和失败处理当作产品能力

没有把“无开发者服务器”简化成“数据不会上传”。项目明确区分：

- 什么数据保存在扩展本地。
- 什么内容直接发送给用户选择的服务商。
- 哪些输入值不上报，但页面附近文字仍可能包含敏感信息。
- 页面变化、取消、超时、重试和部分失败如何呈现。
- 哪些字段永不填写，哪些限制尚未验证。

对涉及个人信息、企业资料或 API Key 的产品，这种边界设计应在第一个原型里出现，而不是等上线前补隐私说明。

### 2.4 使用证据和审查机制，而不是让多个 Agent 重复互相赞同

多 Agent 的价值不在于“投票通过”，而在于分头做竞品、社区、SEO、用户和场景研究，再由父会话核查来源。Qwen 审查也被用于寻找口径矛盾、超证据断言和未来执行者可能误读的指令。

这次有效的协作模式是：

- 事实与链接可追溯。
- 明确哪些是公开事实、推断和未验证假设。
- 不同角色提出反例。
- 由主执行者核对源码和证据后做最终决定。
- 每完成一阶段留下记录、测试、提交和下一步。

### 2.5 主动停止，而不是沉没成本驱动

你最终承认“浏览器填表技术壁垒不高，客户或平台可以自研，现有入口很多，持续付费理由尚未验证”。这会主动放弃已经投入的技术工作，但防止了更大的时间、推广与维护成本。

**一个好的验证体系不仅决定什么时候开始做，也要有勇气按预设门槛决定不做。**

## 3. 可以在下一个项目中避免的偏差

### 3.1 “竞品有的基础功能我都要有”是危险承诺

竞品功能齐全不代表用户需要第二个功能相似的通用工具。它会把注意力从“独有场景、交付方式、渠道和购买理由”拉到功能补齐上。

更准确的表述应是：

> 下一个产品只补齐让目标用户完成一条核心价值链所必需的能力；竞品有但与本场景核心结果无关的功能，不进入首版。

### 3.2 技术样机做得越完整，越容易产生“应该继续”的错觉

当代码、测试、网站和文档都完成时，很容易把工程完成度误当成市场成熟度。后续评估应先问：

- 这些能力中有多少是用户明确要求的？
- 哪一条外部证据会因为产品更完整而改变？
- 继续开发是否能替代访谈、试用、付费或渠道验证？

如果答案是不能，就不应继续增加功能。

### 3.3 研究量不等于一手证据

竞品页面、商店 users、SimilarWeb 类估计、Reddit/HN 讨论、SEO 关键词表都有价值，但它们主要帮助定义问题和渠道，不能单独证明：

- 用户每月真的做多少次。
- 现有工具实际哪里失败。
- 用户愿意切换或付费。
- 某个垂直场景的交付成本可控。

公开研究之后必须尽快进入真实任务观察或受控复现。

### 3.4 搜索流量不能救一个未验证的购买理由

SEO 应先验证“是否存在明确搜索意图”，再投入内容。对于低搜索量、问题发生在行业内部、决策依赖熟人/服务商的产品，SEO 可能不是首要渠道。先确认用户在哪里做决定，再投入网站和内容。

### 3.5 多 Agent 和长评审会放大文档量

独立审查能降低错误，但需要约束：

- 一轮只要求阻塞问题与可执行修正。
- 不让多个 Agent 重复完成同一研究。
- 先给证据来源，再让 Agent 批判结论。
- 以决策门槛为终点，避免无限优化措辞。
- 关键审查集中在高风险判断，不让低风险文字消耗主要时间。

## 4. 建议固化为方法论的“五道门”

这套门槛适合下一个想法快速验证，也可以按风险裁剪。核心不是固定天数，而是不要让后一道门替代前一道门。

| 门 | 要回答的问题 | 最低证据 | 通过后允许做什么 | 应停止或转向的信号 |
|---|---|---|---|---|
| G0 问题门 | 谁在什么触发下完成什么任务？问题是否真实且足够具体？ | 5–10 个公开任务样本、现有流程、替代方案清单、反例 | 做 1 页问题定义；联系目标用户 | 只能描述“很多人可能需要”；找不到明确触发和结果 |
| G1 用户门 | 用户现在怎么做，哪里最痛，为什么仍没被现有工具解决？ | 3–5 次访谈或 2–3 次真实任务观察；至少 2 个不同用户出现同一模式 | 做可丢弃原型或手工服务 | 用户说不出频率/成本；现有方案已足够；只愿意点赞不愿投入 |
| G2 价值门 | 最小流程能否在真实任务中产生更快、更准或更省心的结果？ | 同一任务的手工基线与原型对照；记录总耗时、错误、复核和失败 | 进入付费试点或垂直交付 | 节省无法覆盖迁移/配置/复核成本；结果不可验收 |
| G3 购买门 | 谁付钱、为什么由这个人/预算支付、能接受什么价格和交付？ | 明确购买人、报价、验收标准；至少一次书面试用/付费意向，优先真实付款 | 做可维护版本或有限投放 | 只有口头“不错”；付费人找不到；只能靠免费流量和未来规模化想象 |
| G4 重复门 | 使用会重复吗，渠道可复制吗，收入能否覆盖维护与支持？ | 真实重复使用、复购/续费、稳定获客来源、单位经济性 | 扩大产品、SEO、渠道和招聘 | 一次性需求、高定制、高支持、获客不可复制或客户可轻易自研 |

### 门槛的使用原则

- **不可跨门自证。** 竞品调研不能替代访谈；demo 不能替代真实任务；WAU/注册不能替代付费。
- **门槛要在开发前写死。** 先定义什么结果会继续、什么结果会停止，减少投入后为项目找理由。
- **合成数据必须单独标记。** 它能验证功能，不能单独证明业务价值，且经常高估自动化收益。
- **同一初始态比较。** 手工与工具必须在相同字段、相同资料完整度、相同复核要求下比较。
- **至少分任务子类型。** 例如“首次注册”和“同页多记录”不应因为都属于填表就互相外推。

## 5. 证据阶梯：从信号到生意

建议把每条市场判断标记在下列等级，而不是混成一句“有需求”：

| 等级 | 证据 | 可以支持什么 | 不能支持什么 |
|---|---|---|---|
| E0 想法 | 创始人直觉、AI 推演、朋友认同 | 提出假设 | 产品立项或市场结论 |
| E1 桌面 | 竞品、商店、论坛、SEO、公开工作流 | 任务可能存在；定义替代与渠道 | 频率、付费、真实兼容 |
| E2 用户陈述 | 访谈、问卷、访谈中的具体案例 | 痛点、触发、现有做法、语言 | 实际行为与支付 |
| E3 用户行为 | 真实任务观察、授权页面演示、原型操作、排队/试用申请 | 可完成性、阻力、交互价值 | 留存和商业闭环 |
| E4 可控结果 | 同初始态对照、错误率与总耗时、真实使用留痕 | 可量化增量价值 | 付费与规模化 |
| E5 经济结果 | 付款、验收、续费/复购、获客成本和毛利 | 可支持扩大投入 | 市场永久成立或可忽视风险 |

**FormFill 只有合成资料和受控技术环境中的验证：真实模型调用、真实浏览器运行和真实 MV3 加载都已经验证，这只能说明技术链路可运行，不能升级成市场证据的 E3/E4。项目没有真实授权业务任务观察、同初始态真实手工/工具对照、重复使用或付款，公开研究只到 E1，也没有真实用户陈述的 E2，因此市场证据未达到 E3–E5。合成对照只能作为乐观上限，不能替代真实任务。**

## 6. 下一次想法的 7 天发现冲刺

这是 7 天的**问题与商业验证**，不是 7 天开发完整产品。

### 第 1 天：一页想法备忘录

必须写清：

- 谁在什么情况下遇到什么问题。
- 他现在如何完成，为什么现有方案不足。
- 你能提供什么不同结果，而不是什么功能。
- 购买人、使用者、受益者是否同一人。
- 优先渠道和第一笔收入可能来自哪里。
- 本周要用什么证据决定继续或停止。

若无法写清，不做产品。

### 第 2 天：替代方案与任务证据

检查原生导入、API、浏览器能力、RPA、平台内置、外包服务、Excel 和人工流程。输出：

- 任务发生样本。
- 替代矩阵。
- 你拟解决但已有方案更好覆盖的字段/步骤。
- 尚未被解决的最小价值。

这一天不写产品代码。

### 第 3–4 天：联系 5–8 名目标用户

不要问“你会不会用”，问已经发生的行为：

- 最近一次是什么时候？
- 做了多久，填写多少字段/记录？
- 哪些步骤容易错？
- 现在用什么替代？
- 为此付过什么成本？
- 如果已有工具能完成 70%，剩余 30% 是否值得切换？
- 谁有权批准一次付费试点？

访谈记录必须保留原话、日期、渠道和匿名标识，不能只写总结。

### 第 5 天：可丢弃原型或人工交付

优先用：

- 现有工具 + 人工交付。
- 可点击原型。
- 一张表格/一条脚本。
- 只覆盖一个垂直任务的端到端切片。

目标是验证结果，不验证技术栈。若不用写代码就能完成，就不要先写代码。

### 第 6 天：可验收报价

向真实候选用户提出一个范围非常小的试点，例如：

- 一个页面/一类记录。
- 明确的字段白名单。
- 一份验收标准。
- 一次人工复核。
- 一个明确的截止时间和价格。

拒绝、拖延和“先免费试试”都应是有效信号，不要自动解释成需求。

### 第 7 天：Go / Pivot / Stop 记录

用一页决策记录回答：

- 哪些假设被证据支持？
- 哪些被推翻？
- 哪项结果最不确定？
- 下一步最小实验是什么？
- 触发停止的具体条件是什么？

通过 G1/G2 后再进入 2–4 周最小产品开发；没有通过时，优先改场景、用户或交付方式，而不是继续加页面和功能。

## 7. 从发现进入开发后的执行规则

### 7.1 先做一条完整价值链

首版只做从输入到可验收结果的一条路径：

`获取数据 → 核心处理 → 用户复核 → 结果交付 → 撤销/失败恢复 → 结果记录`

先让这条路径在真实环境成立，再扩格式、平台和自动化。

### 7.2 每个功能必须绑定一个验证问题

不要用“竞品有”作为唯一理由。示例：

| 功能 | 要验证的问题 | 失败条件 |
|---|---|---|
| 批量处理 | 重复任务是否频繁到值得配置？ | 每页只有少量剩余字段，批量增加复核风险 |
| 自动提交 | 用户是否愿意承担无人值守错误？ | 高价值/法规/风控场景要求人工确认 |
| 本地模型 | 数据能否或必须不出本机？ | 用户没有性能、配置或维护条件 |
| 文件导入 | 用户资料是否已结构化？ | 资料分散，清洗成本高于手工填写 |

### 7.3 把隐私边界做成默认架构

- 明确数据发送对象和字段。
- 减少默认采集，历史/学习能力必须单独授权。
- 不在“无后端”口号下省略第三方模型传输。
- 敏感字段、附件、认证和自动提交写入显式边界。
- 一旦暂停某能力，删除路径而不是只改文案。

### 7.4 真实环境验证优先

测试顺序建议：

1. 规则与数据流单元测试。
2. 合成端到端测试。
3. 真实服务接口或真实文件格式。
4. 真实浏览器/平台 UI。
5. 授权用户任务与人工基线。

每个层级都应记录它不能证明什么。Mock 通过不能推出真实兼容，Demo 通过不能推出模型准确。

### 7.5 先设计失败路径

至少验证：

- 超时、取消、网络断开。
- 输入不完整、格式变化。
- 页面/接口在预览后改变。
- 部分成功与回滚。
- 敏感字段或权限不足。
- 付费后交付不达标时的退款/重做边界。

失败路径是产品可信度的一部分，不能等“主流程完成以后再说”。

## 8. 每次实验应留下的最少文档

### 8.1 一页想法备忘录

- 问题与触发。
- 使用者、购买者、受益者。
- 现有替代。
- 核心结果指标。
- 第一渠道。
- 最高风险。
- 停止条件。

### 8.2 假设台账

| 假设 | 当前证据等级 | 支持证据 | 反证 | 下一实验 | 截止时间 | 结果 |
|---|---|---|---|---|---|---|
| 用户每月至少重复 3 次 | E0 | 无 | 无 | 访谈 5 人并记录上月日期 | 第 4 天 | 待定 |
| 现有导入覆盖不足 | E1 | 平台帮助页 | 平台文档声称完整导入 | 用户任务观察 | 第 4 天 | 待定 |
| 用户愿意按次付费 | E0 | 无 | 免费替代丰富 | 书面试点报价 | 第 7 天 | 待定 |

### 8.3 对照实验记录

必须写清：

- 同初始态。
- 字段/记录范围。
- 手工组与工具组顺序。
- 是否包含整理、配置、等待、回源、复核和纠错。
- 失败与重试。
- 数据授权与删除方式。
- 结果可外推到哪些任务，不能外推到哪里。

### 8.4 决策日志

每次只记录一个最终决定、依据、未解决风险和下一步，避免让会议纪要淹没真正的取舍。

## 9. FormFill 中值得复用的资产

- **受控写入协议：** 扫描 → 建议 → 预览 → 应用 → 撤销；页面变化拒写。
- **Excel 单记录隔离：** 只发送选中的一条记录，其他行保留本地。
- **结构映射复用：** 绑定 origin 与表单签名，只存结构，不存值或 Key。
- **多模型适配：** 服务商配置、取消、重试、错误分类和思考参数。
- **真实浏览器测试体系：** Playwright 加载 MV3、真实弹窗、截图与可复现 JSON。
- **隐私与权限文档：** BYOK、数据外发、自动学习暂停、敏感字段边界。
- **调研材料：** 竞品与替代、商店规模、社区发布写法、SEO、用户画像、场景白名单/黑名单。
- **决策与归档体系：** 任务台账、Qwen 审查、提交历史、冻结边界与重启条件。

## 10. 下个想法的最小决策模板

开始写代码前，以下问题必须都能回答“是”或明确标为风险：

- [ ] 有一个具体触发，而不是泛化人群。
- [ ] 找到 3 名以上用户描述最近发生过的真实任务。
- [ ] 现有替代方案被列全，且剩余痛点可描述。
- [ ] 使用者、购买者和受益者已区分。
- [ ] 有可测量的核心结果，不只是“更智能”或“更快”。
- [ ] 已设计同初始态的最小对照方法。
- [ ] 有一条可触达渠道，不依赖“以后做 SEO/投流”。
- [ ] 有明确可验收的试点范围和价格假设。
- [ ] 已写入停止条件与时间盒。
- [ ] 已说明敏感数据、隐私、合规和失败路径。
- [ ] 首版只做一条完整价值链，不追竞品功能清单。
- [ ] 每项后端/平台可替代能力都有“为什么由我们做”的理由。

如果前 4 项中有两项不能回答，进入访谈和任务观察；如果第 7–10 项缺失，暂不建设可维护产品。

## 11. 最终复盘

FormFill 证明了你的执行能力、产品拆解能力和证据意识：你能把一个模糊的工具想法推进到真实模型、真实浏览器、真实文件、完整测试与可交接文档。

它同时暴露了下一阶段更需要的能力：**在工程完成度上升时，保持对需求、渠道、购买理由和维护成本的同等怀疑。** 停止通用产品化不是否定这段工作；它把这段工作转化为一套更成熟的筛选机制，并保留下可以复用的技术组件、测试方法和研究资产。

下一次更快的路径不是“更快写完整产品”，而是：

> 更快找到真实任务，更早做真实对照，更早让购买人参与验收，并在证据不足时更早停止或换场景。
