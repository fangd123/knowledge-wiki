# 01 缘起与技术调研

## 1.1 需求从哪来

项目起点是两个问题：

1. 有没有直接用 Unity、Godot 这类游戏引擎、让 LLM 来做游戏的好方案？
2. 有没有专门用来做游戏的 LLM？

调研之后，制作人把需求落到了玩法上：用 Godot 命令行做一款类似动森的 2D 游戏，玩家用鼠标点地移动，每个居民有自己的话。引擎要能自行准备，图像素材可以用生成服务制作。这是需求转述，不是安装指南。

紧接着又补了一条分工要求：具体实现交给 `codex-delegate`，Claude 负责策划、设计和测试验收。

所以这个项目同时是一次实验：**用两个 AI Agent 分工（一个当策划和验收、一个当程序），从零做出一个能玩的游戏。**

## 1.2 第一轮调研：用游戏引擎 + LLM 做游戏

这是截至本次开发记录（2026-10-17）的一次选型笔记。当时翻过 Reddit 的 r/aigamedev、r/godot 等社区；没有保留下能核对任务、版本和计时口径的逐帖资料。以下只说哪些想法影响了这款小岛游戏，不给社区工具排速度榜。

### 三类方案

| 路线 | 代表 | 适用场景 |
|---|---|---|
| A. 编码助手 + 引擎命令行 | Godot 无界面运行、命令行导入 | 适合改文本场景、批量运行逻辑测试 |
| B. 桥接编辑器 | Godot 或 Unity 的编辑器桥接工具 | 需要读取场景树、预制体或运行画面时 |
| C. 引擎内置辅助 | 编辑器内的生成或补全工具 | 主要在编辑器里制作内容时 |

### 最后留下的三个问题

第一，程序员改的东西能不能直接审？Godot 的 `.tscn` 和脚本是文本，房子的位置和居民的台词也可以放在 JSON 里。第二，改完能不能看见？有人比较过编辑器桥接与命令行的耗时，但一次任务快慢并不能替我们选工具。地图能启动，不代表河里的木筏看起来就是桥。

第三，看见了错处，有没有下一轮？**成败取决于模型外面那套循环。** 于是我们给游戏留了注入鼠标事件和截图的入口；作者验收时看的是那一次真实画面变化，不是实现方对画面的描述。后来桥为什么重做，有[批次开发日志](10-09_批次开发日志.md)可对。

## 1.3 第二轮调研：有没有“游戏专用 LLM”

当时没有找到足以让我们放弃通用编码助手、改选游戏专用语言模型的证据。“写引擎代码”“生成一段能动的画面”“替居民说话”其实是不同的事：

| 方向 | 现状 |
|---|---|
| 写游戏代码 | 有针对 Unity C# 的微调思路；两个接近的评分，没有样本和误差资料，不能据此判断胜负。我们需要的是能交付和检查 Godot 脚本的工具。 |
| 游戏世界模型 | 生成随输入变化的画面，不等于交付可编辑的地图、寻路和存档。 |
| 素材生成 | 本项目后来在选定立绘上比较走路帧，以角色是否跳脸作取舍，见[美术管线](04-03_美术管线.md)。模型名称本身不能代替具体权重的许可。 |
| 游戏内 NPC | 即使让模型扮演居民，**好感度、钱和剧情由确定性的代码控制**。本版用预写台词池，没有接入实时语言模型。 |

## 1.4 调研怎样决定了技术路线

| 调研结论 | 本项目的做法 |
|---|---|
| Godot 文本格式对 AI 友好 | 选 Godot 4.7.2。主场景 `main.tscn` 只放一个根节点，世界全部由代码按 JSON 数据搭出来，Agent 只需要改 `.gd` 和 `.json` |
| 命令行已满足这次工作 | 不另装编辑器桥接。导入、冒烟、测试和截图通过命令行启动 |
| 要让 AI 看见结果 | 游戏里自建截图模式 `--screenshot-test`：用真实注入的鼠标事件走完一套流程，每步截图。验收方每批亲眼看截图 |
| 外部循环决定成败 | 每批固定验收：导入 → 冒烟 → 测试 → 截图 → 人工看图 → 读 diff → 暂存。后来又加了变异测试来检验测试本身 |
| 架构和美术需要审稿人 | 策划先在 `DESIGN.md` 定模块边界，再用实际候选图选脸和步态 |
| 图像分两步制作 | 静态素材用 Z-Image Turbo，走路帧用 FLUX.2 klein 4B，通过图像生成服务出候选，人工挑选 |
| NPC 状态由代码控制 | 台词全部离线写好放在 `data/npcs.json`，好感度、每日限制、对话去重都是确定性逻辑；TTS 只负责“念出来” |

## 1.5 引擎的安装与环境

- 验收方用常规安装的 Godot 4.7.2 stable console 版，保留命令行输出。实现方使用隔离工作区，不能沿用该安装或用户目录。
- `tools/fetch_godot.py` 准备并校验同版本引擎；`tools/run_godot.py` 只为子进程设置测试目录，记录退出状态和报错。
- 这样就有了两套运行环境：Codex 用隔离的 `.tools/` 副本，验收方用正式安装版。后来证明**两种环境都要跑测试**，因为 `user://` 指向的目录不同（见 [06 测试与验收](07-06_测试与验收.md#65-验收中发现的问题)）。
