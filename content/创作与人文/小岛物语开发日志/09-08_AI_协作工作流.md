# 08 AI 协作工作流

这个项目的实质是一次“AI 分工开发”的实践：一个 Agent 当策划和验收，另一个 Agent 当程序员，人类用户当制作人。本文记录这套流程具体怎么运转，以及中途做过的调整。

## 8.1 角色

| 角色 | 由谁担任 | 做什么 | 不做什么 |
|---|---|---|---|
| 制作人 | 用户 | 提需求，在关键分歧上拍板，试听试看 | 不写代码 |
| 策划 / 美术总监 / 验收 | Claude | 调研、写规格、生成和挑选素材、写任务书、跑测试、看图、读 diff、写下一批问题 | 原则上不写游戏代码（Batch G 例外） |
| 实现 | Codex（通过 `codex-delegate`） | 按任务书写代码、测试、工具脚本，交付实现说明 | 不改规格、不改被保护的文件 |

这次这样分，是因为验收时既要问“这段寻路能不能跑”，也要问“这座桥看起来像不像桥”。让一个角色先定标准、再看结果，另一个专心写实现，比较容易发现两者之间的落差；不是所有项目都得用两个 Agent。

用户需要拍板的几个地方：

- 拆成小批次（流程层面）；
- 走路动画用 klein（美术方案）；
- BGM 四个时段都用 MIDI 版（听感）；
- Codex 额度用完后由 Claude 自己上（资源）。

## 8.2 从“一次性交付”到“小批次”

v1 是整包交给 Codex 的：一份完整的 `DESIGN.md`，加一份任务书，Codex 连续工作约 42 分钟，交付了全部代码、数据、测试和截图模式。

v1 验收发现了一串视觉问题。用户随即提出：

> 我觉得你是不是需要给到 codex-delegate 的任务稍微拆一下，然后他干完一个你验收一个这样的，而不是一次性全部给他，最后再验收。

之后所有工作都改成小批次：

| 批次 | 规模 | 内容 |
|---|---|---|
| A | 2 个问题 | 抠图残留、灯光偏绿 |
| B | 3 个问题 | 桥的方向、土路、海岸线 |
| C | 3–4 个问题 | 桥栏杆、HUD、商店面板、动物语导出 |
| D | 3 个任务 | 走路帧处理、帧播放、测试截图 |
| E / E-fix | 1 个功能 + 修复 | TTS 配音；代理、音量、截图稳定性 |
| F / F-fix | 1 个功能 + 修复 | BGM；存档隔离、夜曲静音 |
| G | 1 个功能 | 演示视频（Claude 实现） |

小批次的好处在后面几批很明显：

- 每批改动范围小，`git diff` 一眼能看完，越界改动很容易发现；
- 问题在出现的那一批就被抓住，不会叠加到最后；
- 用户能在中间插入新需求（走路、配音、BGM、视频），不用等“全部做完”。

## 8.3 任务书怎么写

每批任务书只写 2–4 个具体问题，每个问题包括**现象、要求、边界**，最后是**完成标准**。Batch B 的任务书节选：

```markdown
Batch A 验收通过：栅栏抠图干净，夜灯暖色。下面是 Batch B：地图与地面观感。
只改地图生成、地面渲染和桥，其他系统（对话、商店、存档等）不要动。

## B1. 桥的方向不对
截图 03_river_bridge、12_night 里，两座桥的木板是顺着河流方向铺的，看起来像漂在河里的木筏。要求：
- 桥横跨河面。河是南北向，桥就是东西向……
- 寻路：桥格可以走，桥两侧的河水格仍然不能走。保留或补充一条测试，断言河两岸只能经过桥格互通。
……
## 完成标准
- 重新运行地图脚本后 data/npcs.json 和 data/items.json 不变，用 git diff --stat data/ 确认；
- 所有物件不能落在水上或路中间，所有门都能寻路到达；
- tests/run_tests.gd 全部通过，截图模式重跑后，亲自看 03_river_bridge、17_island_overview、01；
- 最后的回复里给出测试命令的实际输出，以及你改了哪些文件。
```

几个要点：

1. **开头先说上一批的验收结论。** 让实现方知道哪些已经确认，不要再动。
2. **现象引用具体截图文件名。** “截图 `03_river_bridge` 里木板顺着河流方向铺”比“桥不好看”有用得多。
3. **要求写成可检验的形式。** “土路面积不超过陆地的 15%”“视觉水陆边界偏差不超过约半格”，验收时可以直接测量。
4. **明确边界。** “其他系统不要动”“只允许 map.json 变化”。
5. **要求测试随功能一起交付。** 每个问题都附带“补一条测试断言……”。
6. **要求交付实际输出。** 不接受“测试通过”四个字，要原始输出和改动文件清单。

修复类任务书（E-fix、F-fix）还会先给出验收方的诊断，并要求实现方**先判断问题属于哪一类**（比如“测试隔离问题”还是“游戏 bug”），再决定改哪里。

上面节选的是当批交给实现方的任务书；它说明了要看哪张图、保护哪些文件，不代替验收结果。

## 8.4 当时那版插件怎样派工

这些是本项目使用那一版插件时的观察，不是今天各版本的操作保证。实现批次接续同一会话（`--resume-last --write`），任务书仍需交代边界，不能指望会话自己记得。后台派发时不在外面套超时器，因为监控进程也可能被一并终止。

状态页只露出很短的进度，任务日志更有用：它能核对已经发出的命令、退出状态和实现方写出的说明，不是对完整思考过程的记录。E-fix 遇到容量不足时要先确认这一批没有完成，再重新派发。

## 8.5 验收循环

```text
           ┌───────────────────────────────────────────────┐
           ▼                                               │
  写任务书（2–4 个问题 + 完成标准）                          │
           │                                               │
           ▼                                               │
  Codex 实现（后台），我盯任务日志                           │
           │                                               │
           ▼                                               │
  读 Codex 的交付报告                                       │
           │                                               │
           ▼                                               │
  自己跑：导入 → 冒烟 → 测试 → 截图                          │
           │                                               │
           ▼                                               │
  亲眼看截图 / 检查图 / 试听；读 git diff                     │
           │                                               │
     ┌─────┴─────┐                                         │
     ▼           ▼                                         │
   通过       有问题 ──► 写进下一批（或 fix 批）任务书 ──────┘
     │
     ▼
  git add -A（暂存作为基线，不 commit），向用户汇报
```

几条执行细节：

- **不和 Codex 同时跑引擎。** v1 验收时一次 `--import` 崩溃（0xC0000005），原因就是和 Codex 同时导入同一个工程。
- **只暂存，不提交。** 每批验收通过后 `git add -A`，下一批的 `git diff` 就只显示新改动。commit 留给用户决定。全部批次完成后，用户要求上传远程仓库，才做了第一次提交并推送到 Gitee。
- **验收结论用用户能看懂的话汇报。** 只说改了什么、效果如何、还有什么需要用户决定，不贴测试日志。

## 8.6 什么时候策划方自己动手

原则上策划方不写游戏代码，但有几类工作一直是策划方自己做的：

- **调研和规格**：`DESIGN.md`、各批任务书；
- **素材生成和挑选**：ComfyUI 出图、选图，klein 改图、选帧（实现方只写处理脚本）；
- **接口探测**：TTS 接口的参数、UA、代理问题都是先摸清楚再写进任务书；
- **对比实验**：走路动画的三种模型对比、ACE-Step 的 AI 曲候选和试听页；
- **最后一批**：Codex 额度用完后，Batch G 的导演脚本、录制工具和测试都是 Claude 自己写的，验收流程照旧。

## 8.7 经验教训

1. **这次小批次更合适。** v1 一次交完，验收才看见桥、岸线和商店面板都有问题。分批后，下一张任务书可以直接引用刚看过的那张图。
2. **任务书的质量决定实现质量。** 引用截图文件名、给可测量的标准、划清边界，比任何“请认真实现”都有效。
3. **实现方报告“通过”不等于真的通过。** 本项目所有被发现的问题，在实现方的报告里都是“通过”。验收方必须自己跑、自己看。
4. **两个 Agent 的运行环境差异本身就是测试资源。** Codex 的隔离环境和验收方的真实环境不同，正是这个差异暴露了测试读真实存档的问题。
5. **人做关键选择。** 走路动画方案、BGM 风格这类主观判断，给用户准备好对比材料（对比图、试听页），让用户拍板。
6. **配置记得住选择，不能替你保管原件。** 要换一张图，原候选还在，才可以改清单重跑后处理；否则要重新准备模型、生成并挑图。换声还依赖对应服务，重渲染音乐需要音色库。哪些成品留了、哪些候选没归档，见[已知问题与后续方向](11-10_已知问题与后续方向.md)。
