# 10 已知问题与后续方向

## 10.1 已知问题

当前没有阻断运行、逻辑测试或截图模式的问题。下面列的是表现上的限制、技术债，以及工程管理上待处理的事。

### 美术与表现

| 问题 | 说明 | 可能的改法 |
|---|---|---|
| 只有正面走路帧 | 角色向左右走时靠水平翻转，向上走时仍然显示正面，没有侧面和背面帧 | 用 klein 以同样的流程生成背面和侧面的 a/p/b 帧；`walk_frames.json` 增加方向维度，`actor.gd` 按移动方向选帧 |
| 部分居民的步态偏弱 | klein 对“左脚在前 / 右脚在前”区分不稳定，同一角色常抬同一只脚。挑选时兔子（棉花）的 a / p / b 三帧都是 passing 姿态，走起来更像轻微晃动 | 换种子或换提示词重生成兔子的跨步帧；或者给兔子单独做“蹦跳”式步态，更符合角色 |
| 遮挡淡化用包围矩形 | 高物件判断是否挡住玩家时用纹理的包围矩形，玩家走到树冠透明的角落时也可能提前淡化 | 改用 alpha 掩码采样，或者为树冠设一个更紧的椭圆判定区 |
| 岛名不统一 | `data/map.json` 的 `world_name` 是 `"???"`，界面上的“风铃岛”写死在 `interface.gd` 里 | 把 `world_name` 改成“风铃岛”，界面改为从地图数据读取 |
| 演示视频没有字幕 | 第一次看的人不一定能理解“送喜欢的礼物好感 +3”之类的机制 | 在 `demo_director.gd` 里按分镜时间加字幕层，或者用 ffmpeg 叠字幕 |

### 功能

| 问题 | 说明 |
|---|---|
| 没有改名界面 | 玩家名默认“小岛友”，只能改存档里的 `player_name`。改名后，含 `{player}` 的台词就不在离线语音里，会走在线 TTS |
| 12 句动态台词需要联网 | 含 `{time}` / `{day}` 的 12 句无法离线预生成。离线时这些句子用 beep 代替，截图模式和演示模式也一样 |
| 没有打包发布 | 目前只能用 Godot 编辑器或命令行运行，还没有配置导出预设，也没有生成 exe |

### 测试与工程

| 问题 | 说明 | 建议 |
|---|---|---|
| 断言数随帧率浮动 | 音乐曲线检查按实际帧采样，所以每次运行的断言总数略有不同 | 判断测试结果看 `0 failures`，不要比较断言总数 |
| 部分原始素材不在仓库 | `.gitignore` 忽略了 `_raw/*.png`（原始生成图）、`_raw/walk/*.png`（约 200 张走路候选）和 `_raw/voice_cache/`（TTS 原始 MP3）。ACE-Step 的 12 首候选曲只在会话临时目录 | 这些都可以用脚本重新生成，但依赖 107 服务器和 TTS 接口。若希望完整归档，可另存到 NAS，不放进 git |
| 生成工具依赖外部环境 | 美术重建依赖 107 服务器的 ComfyUI；配音依赖 TTS 接口；作曲依赖本地 FluidSynth 和音色库（放在 `.tools/`，不进版本控制） | 见 11 附录 的准备步骤 |

## 10.2 后续方向

按“投入小、收益大”排序：

### 第一档：补完现有体验

1. **背面和侧面走路帧。** 管线已经成熟，主要成本是生成和挑图。
2. **统一岛名，加改名界面。** 开场让玩家输入名字和岛名，存档已经有 `player_name` 字段。
3. **导出 Windows 版本。** 配置导出预设，确认字体、语音、音乐都能正确打包。
4. **演示视频加字幕。**

### 第二档：扩充玩法

5. **钓鱼和捉虫。** 动森的核心收集玩法。可以沿用现有的“点击物件 → 走近 → 交互”流程，物品表增加鱼、虫和对应售价。
6. **家具和室内。** 用铃钱买家具、布置自己的房子。需要新的场景切换和网格摆放系统。
7. **更多居民。** 美术（静态图 + 走路帧）、台词、配音都有现成脚本，新增一位居民主要是数据工作。
8. **季节和天气。** 时段系统已经能切换 BGM 和光照，可以扩展到雨天、季节配色。

### 第三档：LLM 驱动的居民

9. **LLM 自由对话。** 现在的台词是预写的台词池。可以接入 LLM，让居民根据好感、时间、背包内容、最近发生的事即兴说话。按调研时的结论，**状态必须由代码掌握**：好感、物品、铃钱只能由游戏逻辑修改，LLM 只负责生成文本，不能直接改游戏状态。
10. **实时配音。** 在线 TTS 链路（代理、缓存、迟到结果丢弃）已经在 Batch E 打通，LLM 生成的句子可以直接走这条路。

## 10.3 如果重新做一遍

- **一开始就拆小批次。** v1 整包交付后的问题太多，返工了三批（A、B、C）。
- **一开始就把测试和真实用户数据隔离。** F 批的 43 条失败本可以避免。
- **一开始就做两种运行环境的测试。** 实现方的沙箱和真实环境的差异暴露了好几个问题，越早发现越好。
- **走路帧在选素材时就一起规划。** 静态精灵和走路帧分两次生成，导致需要额外做对齐和校色。如果一开始就用同一个模型、同一套提示词生成待机和走路帧，后处理会简单得多。
