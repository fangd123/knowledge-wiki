# 03 美术管线

游戏里所有图像素材都是 AI 生成后经脚本处理的，没有手绘，也没有从网上下载现成素材。地面、水面、桥面、灯光和界面则是用 shader 和代码画的。

```text
提示词表 ──► ComfyUI 批量生成（每件 2 个变体）──► 联系表 ──► 人工选图（_raw/selected.json）
                                                                 │
                       ┌─────────────────────────────────────────┴──────────────┐
                       ▼                                                        ▼
           process_assets.py 抠图 → assets/sprites/（33 张）         gen_walk_frames.py 改图出走路候选
                                                                                 │
                                                       人工选帧（_raw/walk/selected.json）
                                                                                 │
                                                  process_walk.py 对齐/校色 → assets/sprites/walk/（35 张）
```

## 3.1 美术方向

- **风格**：Q 版（chibi）、柔和粉彩、深棕色粗描边、平涂赛璐珞阴影。角色大头小身子，正面三分之四视角。
- **为什么用粗描边**：抠图时描边是天然的分界线，可以提高抠图的稳定性；同时也统一了 AI 图在不同种子下的画风。
- **为什么不用像素风**：设计目标是“慢生活、有氛围”，柔和的平滑美术更接近动森；纹理过滤用 linear。

统一的风格提示词（`tools/assets_spec.py`）：

```text
2D game sprite for a cozy life simulation game, cute chibi style, soft pastel colors,
clean bold dark brown outline, flat cel shading, full body, centered,
isolated on a completely flat solid {bg} background, no ground, no shadow, no text, no border
```

角色还会拼接一段角色模板：`anthropomorphic animal villager standing upright on two legs, big round head and small body, facing the viewer, three-quarter front view`，再加上各自的外貌描述，比如橘子是“系着草莓图案黄围裙的橘色虎斑猫女孩”，阿福是“穿宽松浅蓝卫衣、手拿饼干的瞌睡柴犬男孩”。

建筑统一加 `seen from a top-down three-quarter view`，和俯视角地图对齐。

## 3.2 素材清单

共 32 个生成项、33 张入选图（玩家的家用的是蓝屋顶房子的另一个变体）：

| 类别 | 素材 |
|---|---|
| 角色（7） | 玩家、橘子、阿福、棉花、老熊、嘎嘎、狸叔 |
| 建筑（7） | 红 / 蓝 / 绿 / 黄 / 紫屋顶住宅、玩家的家、商店 |
| 植物（8） | 普通树、果树、松树、椰子树、灌木、红 / 黄 / 白花丛 |
| 场景物件（5） | 石头、告示牌、栅栏、邮筒、路灯 |
| 物品（6） | 苹果、贝壳、树枝、郁金香、椰子、铃钱图标 |

## 3.3 生成：107 服务器上的 ComfyUI

- **模型**：Z-Image Turbo（int8 量化，Apache-2.0），文本编码器 Qwen3 4B，跑在内网 107 服务器的 3090 上，ComfyUI 端口 8189。
- **参数**：8 步，CFG 1，采样器 `res_multistep`，调度器 `simple`，AuraFlow shift 3。角色 896×1152，建筑和物件 1024×1024。
- **脚本**：`tools/gen_assets.py` 通过 ComfyUI 的 HTTP API 提交工作流，每件素材出 2 个变体（种子 1000、1001），原图存到 `_raw/<id>_<seed>.png`，已存在就跳过。
- **选图**：`tools/contact_sheet.py` 把候选拼成联系表，人工逐个挑选，结果记录在 `_raw/selected.json`（key 是游戏内素材名，value 是原图文件名）。

选图看三点：轮廓是否完整干净，同类素材之间画风是否统一，以及特征是否符合设定（比如阿福手里要有饼干，嘎嘎要戴贝雷帽）。

## 3.4 抠图

### 实际情况比预期复杂

提示词要求“纯色背景、无投影”，但生成出来的背景其实是浅粉或浅绿，带轻微渐变；物体下方有一块同色系的深色椭圆投影；个别图上还散落着小草点，路灯周围有一圈光晕。

所以 `tools/process_assets.py` 的规则是按这些实际情况设计的：

1. **背景色**：取四条边像素的中位数。
2. **候选背景像素**，满足其一即可：
   - 和背景色 RGB 距离 < 54，且色相接近；
   - 投影规则：色相差 < 0.075，饱和度不超过背景 +0.19，亮度不低于背景的 65%。也就是“同色相、更深一点的背景色”。
   - 路灯光晕：允许更大的色相偏移，但要求有一定饱和度。
3. **近白色保护**：要求候选像素的饱和度至少是背景的 45%。白兔、白鸭、栅栏的浅色部分色相不稳定，靠饱和度和粉绿背景区分开，不会被吃掉。
4. **连通性**：从四边做洪水填充得到外部背景；封闭空隙（比如栅栏格子之间）用同一套颜色规则判断。
5. **去碎块**：只保留面积 > 160 像素、且不小于最大连通块 0.8% 的前景区域，散落的草点和反光会被去掉。
6. **羽化和去色溢**：alpha 做 0.65 px 高斯模糊；半透明边缘像素按 alpha 反解，把背景色成分减掉，避免边缘残留一圈粉色或绿色。
7. **裁剪**：裁到不透明区域的包围盒，留 8 px 边距，长边缩到 ≤ 512 px。

### Batch A 修过的一个漏检

v1 的抠图只从四边做洪水填充，栅栏木条之间的封闭空隙没有连到边上，留下了浅绿色背景块。当时的检查图是棋盘格底，浅绿色混在灰白格子里看不出来，验收也就漏掉了。

修复分两步：

- 封闭空隙和外部背景共用同一套颜色判定，33 张素材全部重新生成；
- 新增深色底检查图 `_raw/cutout_check_dark.png`（底色 `#203020`），浅粉、浅绿残留在深色底上非常显眼。之后每次验收都同时看两张检查图，并放大复查栅栏、兔子、鸭子、路灯。

这个教训后来变成了一条通用经验：**检查图的底色要和你想发现的问题形成反差。**

## 3.6 地面：一个 shader 画整片地

规格明确要求**不用瓦片贴图**。整片地面由 `scripts/ground.gdshader` 一个 shader 画出来，避免出现格子感。

### v1：每格 1 像素的数据纹理

v1 把 64×44 的地形网格写成一张 64×44 的小图，linear 过滤后在 shader 里按地形类型加噪声：

- 草地：两三种绿色的低频噪声斑块，加细碎的小草点；
- 沙滩：暖米色加细颗粒；
- 土路：浅棕，边缘柔和；
- 海和河：缓慢流动的色带加闪光，靠岸处有随时间起伏的白色泡沫线。

问题是边界精度只有一格。路是矩形块，海岸有锯齿。

### Batch B：距离场

`tools/terrain_fields.py` 从地图离线烘焙一张 512×352 的距离场 `assets/terrain/fields.png`，每格 8×8 个采样：

- 海岸和河岸从原始格边平滑，烘焙偏移最多 10 px，shader 噪声扰动最多 2 px，合计小于半格（16 px）。这样视觉上的岸线不会偏离寻路用的格子太多，角色不会看起来像走在水里。
- 道路直接用生成曲线的距离场，宽 1.1–1.35 格，边缘柔和。
- 新增浅水带和浪花。

地图 JSON 和距离场 PNG 必须一起更新。`tools/build_data.py` 会确定性地重建两者；如果只手改了 `map.json`，用 `terrain_fields.py` 单独重烘焙。

### 桥

- 桥面在 shader 里画：木板南北排列，两侧深色边框和短柱；每端延伸 16 px 到岸上。
- Batch C 增加了 `scripts/bridge_rail.gd`：桥南北两侧各一排 21 px 高的立柱和横木，放在 Y 排序层里，角色走过时会被正确遮挡。它只是视觉节点，不影响寻路。

## 3.7 灯光

v1 按规格用了 `PointLight2D` 加法光。验收发现路灯光偏绿：光色和绿色草地、蓝色 `CanvasModulate` 相乘后，暖黄色变成了黄绿色。

Batch A 改成 **unshaded 的径向透明 sprite**：颜色 `#ffc870`，路灯半径 110 px，中心亮、边缘柔和衰减；用透明混合而不是乘法，所以颜色不受地面和环境色影响。18:00–19:00 线性渐亮，05:00–06:00 线性渐灭，白天隐藏。房屋窗户用同样的暖色和时段。

## 3.8 界面

- 字体：ZCOOL KuaiLe（站酷快乐体，OFL 协议）。Codex 发现全新缓存下第一次 `--import` 时，主题会在字体导入之前初始化，于是用 `tools/bake_font.gd` 把 TTF 字节烘焙成原生资源 `default_font.res`，首次导入也能用。
- 主色调：奶油色面板 `#fff8e7` + 深棕描边 `#8b6b4a`，名字牌用居民主题色。
- 对话头像直接裁静态立绘的上半身，不另外生成。

## 3.9 逐帧走路动画（Batch D）

### 需求

v1 的角色只有一张正面立绘，走路靠程序化动画：上下弹跳、左右摇摆、落地压扁。用户的反馈是：

> 任务在走路的时候，我想更加逼真一些，身体四肢的动作那种，你看看是不是要生成不同走路姿态的图片来弄。

目标定为：每个角色 3–4 帧正面走路姿态，和原立绘保持同一张脸、同一身衣服、同一个大小。

### 模型对比

用户要求“看看其他的模型行不行”，于是在 107 上对比了三种方案：

| 方案 | 结果 |
|---|---|
| **FLUX.2 klein 4B 参考图改图** | 头部位移 ≤ 1 px，步伐清楚，约 6.5 秒一张 |
| Qwen-Image-2.1 edit | 角色缩放最大变化 12%，位移最大 35 px，帧间会跳 |
| MiniMax H3 视频（首帧 = 尾帧） | 角色几乎不走；猫的脸在中间帧变了 |

逐帧动画最怕帧间抖动，klein 的头部稳定性明显最好，用户拍板“就用 klein”。

### 生成

`tools/gen_walk_frames.py` 以选定立绘为参考图，用 klein 4B 改图（4 步，896×1152）。提示词模板：

```text
Edit this image: the same character is walking in place toward the viewer, a small natural walking step. {pose}
Arms stay close to the body with a small swing, not raised. Keep everything else identical: same face, hair,
outfit, {extra}colors, proportions, size, head position, outline thickness and flat art style.
The background stays the exact same flat solid color, with no shadow on the ground.
```

- `{pose}` 有三种：左脚前迈（stepL）、双脚并拢的过渡帧（pass）、右脚前迈（stepR），手臂和腿反向摆动。
- `{extra}` 点名改图时容易丢的细节：猫的条纹尾巴、狗手里的饼干、鸭子的小本子、浣熊的环纹尾巴。

### 坑：模型不分左右脚

生成后发现，同一个角色不管提示词写左脚还是右脚，模型总是抬同一侧的脚。

解决办法是“镜像技巧”：加 `--mirror` 参数，先把原图水平翻转再改图，结果翻回来，就得到另一侧的脚（文件名带 `m`，如 `stepLm`）。角色左右基本对称，翻转两次对外观影响很小。

### 选帧

总共生成了约 200 张候选。先用脚部扫描指标（feetscan）粗筛，但它只能大致判断两只脚分开多少，分不清哪只脚在前。最终靠**放大腿部裁剪图人工判断**。

选择记录在 `_raw/walk/selected.json`：

- 循环是 a（一侧脚在前）→ p（过渡）→ b（另一侧脚在前）→ p2（第二个过渡帧，可省略，省略时复用 p）；
- a 和 b 不一定来自 stepL / stepR 的候选。有些角色（如棉花）没有合格的迈步帧，就用几个姿态略有差异的 pass 帧组合，保证整体不跳、不变形。这是质量和逼真度之间的取舍。

### 后处理：`tools/process_walk.py`

AI 改图出来的帧，在位置、大小、颜色上都会有细微漂移，直接播放会闪。处理步骤：

1. **抠图**：复用 `process_assets.py` 的 `cutout_canvas()`，在原始 896×1152 画布上抠，不单独裁剪。
2. **头部对齐**：取头顶往下身体高度 25% 的区域，在 ±6 px 内搜索整数平移，用预乘亮度和透明度的误差对齐，不缩放。水平中心只看头部（不然狗伸出来拿饼干的手臂会把中心拉偏）。
3. **统一裁剪**：一个角色的全部帧取联合包围盒，加 12 px 边距，统一缩放到长边 512。
4. **校色**：
   - 先在上半身 60% 的平坦区域拟合 RGB 仿射变换（增益限制 0.85–1.2，偏置 ±20）；
   - 再按整个前景的 32 个颜色簇做强度 0.9 的局部校正，修复衣服和毛色发灰。
   - 颜色簇按相同位置的平坦像素配对，避免姿势变化导致粉色腮红被错配成书页的米黄色。
5. **记录**：每帧的平移、校色参数、校色前后 RMSE 写进 `assets/sprites/walk/walk_frames.json`。校色后稳定前景的 RGB RMSE 在 1.9–3.1 之间（0–255 刻度），头部平移最多 4 px。
6. **检查图**：`_raw/walk_check.png` 和 `_raw/walk_check_dark.png`，每行 idle/a/p/b/p2，蓝线标头顶、橙线标共用脚底；`_raw/walk_check_game.png` 按游戏内 72 px 的比例显示。

### 游戏内播放

- 按**走过的距离**换帧，而不是按时间：玩家每 13 px 换一帧，居民每 9 px。这样快走慢走都不会“滑步”。
- 循环 a → p → b → p2；起步的第一只脚随机，左右交替。
- 逐帧走路不再压扁和旋转，只在过渡帧上抬 2 px，模拟重心起伏。
- 停下或对话时立刻回到待机图，待机保留 1.00–1.02 的呼吸缩放。
- 缺少某个角色的帧数据时，自动退回旧的程序化动画。

## 3.10 美术经验小结

1. **提示词约束不等于实际输出。** 要求纯色背景，拿到的是渐变加投影。处理脚本要按实际输出设计。
2. **检查图底色决定能发现什么问题。** 棋盘格底漏掉了浅绿残留，深色底一眼就能看到。
3. **逐帧动画的头号敌人是抖动，不是姿势不够大。** 选模型看头部稳定性，后处理再做对齐和校色。
4. **自动指标只能粗筛。** 左右脚这种语义问题，最后还得靠放大图人工判断。
5. **能用代码画的就别生成。** 地面、水、桥面、灯光、界面都是 shader 或代码绘制，可控、可调、没有接缝。
