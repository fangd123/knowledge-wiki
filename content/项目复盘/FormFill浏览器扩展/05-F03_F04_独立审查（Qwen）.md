## 一、总体判断（先说值得保留的）

propose/apply 分离干净：propose-fill 走同意闸→scan→模型→build-preview，全程不写页（background.test 断言消息序列仅 get-form-context/build-preview）；apply-fill 只转发不调模型，同意闸独立复查。buildPreview 纯读（测试断言 DOM 未变）；applyPreview 的 stale 整体拒写 + 逐项表单签名复查 + 保护判定复查 + include 过滤四层齐全；"已有值默认不勾"在 Popup 决策初始化正确实现且有测试。撤销快照确实只在内容脚本模块内存、刷新即丢，与政策新段落一致。"当前值不发模型"属实：propose 链路中模型只见扫描摘要（checkbox/radio 仅 value 属性），currentValue 在模型返回之后才由 build-preview 读取，仅回传 Popup。文档双语对等、网站 5 步文案与实现一致（但见 C3 台账不实）。

## 二、发现（severity / 位置 / 证据 / 建议）

### C1（中高，需修改）radio 撤销无法恢复原选中项，且虚报 restored
- 位置：`entrypoints/content.ts` `snapshotForUndo`/`applyValue`(radio 分支)/`undoLastFill`。
- 机理：applyValue 把 checked 设在**匹配到的组内 radio**（可能是另一个元素），而快照只记录**定位到的元素**。撤销时只把定位元素设回 false，原选中项不会恢复；radio 组互斥导致整组全空。
- 实证（我在 %TEMP% 用仓库 vitest 配置外挂临时测试复现，未改仓库文件）：A/B 组 B 默认选中，建议选 A → apply filled，checked=[true,false]；undo 返回 `{restored:1,skipped:0}`，checked=[false,false]，期望 [false,true]。
- 为什么重要：直接违反本批新增承诺——README"只恢复本次写入且未被你改动的字段"、隐私政策"undo restores only fields written by that fill"、网站"本次写入可一键撤销"。用户数据（原选择）丢失且 UI 报成功。现有 8 项 preview-flow 测试全部只覆盖 text/textarea，radio/checkbox/select 撤销零覆盖（见 C6）。
- 建议：快照改为**组级**——apply 前记录同 form 同名组内全部可用 radio 的 checked 状态与被写元素；undo 时若组内当前状态仍等于写入后状态则整组恢复，否则 skip。同时补 checkbox 与 select（含 multiple）撤销测试。

### C2（中，建议本批处理或明确降级口径）radio 的"已有值保护"被绕过
- 位置：`content.ts` `buildPreview` 中 `readCurrentValue` 对 radio 只读**定位元素自身**的 checked。
- 实证（同上脚本）：B 选中时，locator name=plan 定位到 A，preview 报 `currentValue="" hasExistingValue=false` → Popup 默认勾选 → 一次点击即覆盖用户已选的 B。
- 为什么重要：本批核心承诺"已有值的字段默认不勾选，勾选后才覆盖"对 radio 组不成立；组内已有选中就是"已有值"。这不是注入漏洞（仍需用户点应用），但保护语义与文案不符。
- 建议：radio 的 currentValue/hasExistingValue 按**组**判定（组内有 checked 即已有值，展示选中项的 label/value），默认不勾。若认为改语义成本高，至少在本批文档中如实注明"单选组已有选中时仍默认勾选"，但我不推荐——与商店文案冲突。

### C3（低中，台账/证据口径）声称的"FEATURES 4→5 卡加预览复核"未发生

### C5（低，备注）撤销的次级边界
- `lastFillUndo` 仅在有条目时替换：第二次 apply 全部 skip 时旧快照仍在，"撤销本次填写"实际撤的是上一次——语义可辩（上一次写入仍未撤），但 undoHint 说"this fill"，建议全 skip 时清空或文案改为"撤销最近一次写入"。
- undoLastFill 不复查保护判定：若字段在 apply 后被页面设为 readonly/disabled，undo 仍写入。风险低（恢复的是用户原值），可留 F04 后续。
- stale 判定依赖 href+签名，SPA 改 href 但表单未变也会整体拒写——保守方向，正确，无需改。
-  orphan（form 外）控件无 formSignature，仅靠全局 scanToken 兜底；scanToken 含全部表单签名，实际覆盖足够，注明即可。
