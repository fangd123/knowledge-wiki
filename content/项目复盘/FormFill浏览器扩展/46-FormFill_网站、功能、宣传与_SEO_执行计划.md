# FormFill 网站、功能、宣传与 SEO 执行计划

计划日期：2026-11-17，Asia/Singapore。接续现有调研与 Qwen 独立复核。本文件规划下一阶段工作；表内实现、上线、用户招募、付费实验均尚未执行。最终策略处理见 [复核处理记录](50-Qwen_独立复核：处理结果与统一决策.md)，研究事实见 [总报告](35-FormFill_全面评估：网站、竞品、市场表现、产品策略与_SEO.md)。

同一 Qwen Agent 已完成 [计划定向复核](49-执行计划定向一致性复核（qwen4-max-preview）.md)，同意作为下一阶段实施基线，无根本分歧或实质性阻塞。父会话已补入其关于 G1 内部先后顺序的澄清；这表示计划口径一致，不表示待办已执行或市场假设已成立。

**阶段目标：先让用户能可靠地完成一次填写，再证明某一种任务值得反复使用，之后才扩大宣传或收费。** 官网暂用“把已有资料，填进网页表单”；“合作伙伴登记”作为候选场景，不先锁定整个产品。

## 1. 执行方式与阶段门槛

按一名主要开发者兼顾产品的保守组织方式排队；这是假设的人力配置，不是已确认的资源。开发同时推进一个功能包，内容工作可独立整理事实、截图脚本和帮助页。复杂度 S/M/L 只表示相对工作量，不换算为未经估算的工日。每个 M/L 项先验证关键实现，再确定工时和日历日期。

| 阶段 | 必须得到的结果 | 进入下一阶段的依据 | 可以并行的工作 |
|---|---|---|---|
| G0：发布基础 | 隐私行为和文案一致；真实获取/支持入口；Demo 与布局缺陷修复；一个已选浏览器/模型组合真实跑通 | 原已知缺陷有对应回归证据；干净环境完成安装、连接、填写、人工检查 | 观察候选用户的手工任务；整理安装和数据流说明 |
| G1：受控试用 | 填前预览、保护已有值、跳过/取消、支持范围内的撤销；多记录任务有明确选记录 | 用合成资料验证目标页面、记录主体与写入值一致；错误能被发现和解释；适用任务有可运行样例 | 少量自愿技术测试；比较手工、原生导入、规则工具和最接近的 AI 工具 |
| G2：需求与复用 | 候选工作流的真实频率、总耗时、配置负担与再次使用记录 | 至少出现可具体描述的重复需求，并确认现有替代不足；小样本只作投入判断 | 已完成任务的教程；按规则获取技术反馈；可用官网的基础索引 |
| G3：最小差异与商业实验 | 根据 G2 只选择一个重点：结构化映射复用，或来源检查；明确交付范围和成本 | 用户实际复用；如试收费，需可验收交付、真实付款与可承担成本 | 有证据的场景内容、经同意的案例和有边界的支持 |
| G4：扩大有效渠道 | 同一任务被更多独立用户使用，支持负担可控 | 扩展渠道带来匹配的试用/复用，或持续付费需求；不能仅看曝光 | 有选择地扩语言、教程、兼容范围和收费形式 |

G0 的技术复现不必等完整新功能；G1 的真实业务试用需要相应控制能力。纯访谈和手工任务观察可立即开始。公开演示、网页内容和社区反馈随能力成熟逐步发布，不需要等到收费功能全部完成。

G1 内先实现 F03/F04 并完成合成资料验收，之后才开始真实业务试用；涉及多记录时，同样先完成 F05 的记录选择与主体隔离验收。阶段表的门槛是完成本阶段、进入下一阶段的依据，不意味着未验收版本可以提前给业务用户使用。

第 30、60、90 天从执行启动日起作为复盘点：检查完成了哪些门槛、阻力在哪里、是否继续投入，不承诺到某天完成所有中高复杂度功能。没有再次发生任务，记录“未观察到复用机会”，不直接算流失。

首页暂保持通用能力定位；内容顺序为：任务和入口 → 真实演示 → 文字/Excel/Word 例子 → 安装与模型设置 → 数据流和限制 → FAQ、支持、源码、版本记录。用现有视觉体系修正信息层级与可用性，先不启动全站视觉重做。

| W02 / P0 / S–M | 获取和支持闭环；`website/src/site-links.ts`、安装区、仓库发布说明 | 匿名浏览器和目标用户环境能访问仓库/README/包；若不可达，提供实际 Release 或镜像再验证。链接真实、发行者一致；无假商店链接/占位邮箱；给版本、权限理由、失败入口；干净环境可加载 | 正式域名/支持地址/发行身份需落实；本轮 Gitee 匿名 HTTP 返回 403，仅证明该次请求失败，真实浏览器可达性仍待验 |

| F07 / 条件性 P2 / L | 来源检查的最小增量实验 | Excel 单元格定位可利用 F05 的结构；文本/Word 先验证原文片段定位是否减少检查时间；source ID 必须可在本地解析；区分原文、转换、缺失、冲突 | 先观察“找出处”是否为主要阻力；跨文档、复杂 Word 追溯另立范围，不与 F06 捆绑开发 |

**关于安全和收费：**本计划建议隐私控制、已有值保护、基础预览和有限撤销作为免费可靠性能力；这是产品选择。MIT 允许商业收费，也允许取得代码者按许可复用/分发，不能靠收费撤回已有授权。

## 4. 客群、价值与价格验证

先对照两个候选任务；不按主观行业印象选定结果。

| 候选 | 需要观察的重复单位 | 应与什么比较 | 否定或改变方向的信号 |
|---|---|---|---|
| A：同一公司资料→不同合作伙伴登记网页 | 同一资料是否经常遇到新网页；同一网页是否会再次使用 | 手工复制、浏览器 autofill、通用 AI 工具 | 每个网页只填一次、字段少且手工快；逐站适配成本无法摊销 |
| B：同一业务网页→多条结构化记录 | 同一表单/模板被不同记录反复使用 | 系统原生 CSV 导入/API、XL2Web 类规则映射、手工和 AI | 原生导入已解决；模型或扩展增加核对负担；企业环境不接受当前安装/接口方式 |

首轮计划观察 5–8 名自愿用户，尽量覆盖两类任务；这是研究工作量建议，不是统计显著性设计。记录上个月实际次数、每次字段量、现有替代、安装/API 权限与配置能力、谁付款。先看手工过程，再用难度相近的合成任务比较，不向没有发生过任务的人只问“你会不会用”。

**任务记录最少字段：**匿名任务 ID、候选类型、来源结构、目标网页/控件类型、版本/模型、是否首次使用、字段总数、正确/错填/漏填/无依据填入、错误主体、配置/操作/等待/复核/纠错各耗时、API 费用、是否再次发生任务/再次选择使用、拒用原因。研究记录不保存 Key、真实文件正文或真实表单值；失败例用合成资料复现。

选择固定的小型合成任务集：普通、缺失、多记录/同名、冲突/格式差异，覆盖已选普通控件。先跑最小集合找阻力；证明稳定性时才扩模型与重复次数。错误字段、漏填字段均进入分母，不只报“已填字段准确率”。同时观察首次配置和复用两种成本。

### 收费分支

1. **当前免费预览继续改善。** 不把未开发功能写成可购买套餐。
2. **可选的限定适配服务。** 只有重复使用能摊薄交付费、已有可验收能力且工时可控时，才以原 ¥699/次作为一轮报价假设：一个资料模板、一个网页、最多 20 个普通字段、一个浏览器/模型组合、配置或代码、合成验收样例、说明、一次最多 60 分钟指导、验收后 14 天范围内缺陷修正。网站改版、新模板/网站另评估，API 另付。先讨论任务、范围和价格，再决定新增开发；口头接受不计收入。
3. **可规模化的软件收费另验证。** 服务有人买不等于订阅成立。若多个客户共同需要规则维护、组织配置或分发便利，再比较标准产品权益、托管服务或维护包；不要为收费先建账户和支付后台。
4. **年度维护暂不报价。** 原 ¥199/年缺少成本和持续需求依据，已撤出当前建议；不是改成另一个无依据金额。先记录共用规则维护频率、每客支持量及可覆盖工时。

**多记录服务的收款前置：F05 明确选记录与主体隔离已实现、可试，并以至少两条相似主体记录证明不串填。** 报价/验收单须写清是“同一表单×多记录”还是“同一资料×约定网页”，不能以开发中的能力交付并收款；跨网页仍按约定单表单范围核算，不自动包含任意新网站。

报价前填写：`可用交付工时 = (报价 − 税费/支付/退款准备 − 其他直接成本 − 目标贡献) ÷ 内部小时成本`。内部小时成本和目标贡献由实际资源决定。对照预计开发、配置、支持、返工及可归属获客工时；若超出，调整范围/价格或不接。公共研发与单客交付分别记录，不能漏掉公共研发成本后声称产品高毛利。

首轮同范围向 3–5 位有已观察需求的人验证报价，记录收到报价、试用、验收、实付、退款及原因。至少两位无关联客户实付、实际复用且贡献可承担，最多支持继续探索；不能据此宣称产品市场匹配。没有持续需求，不卖年包。

## 5. 宣传计划

宣传对象分为任务用户与技术反馈者。初始市场按人民币试点、中文可服务用户组织；不由此假定全部用户都在中国大陆。招募时记录实际地区、浏览器、扩展获取方式和模型服务可用性；若主要用户在大陆，不能默认 Chrome 商店和 Google 就是可用的主渠道。

| ID / 阶段 | 工作与交付 | 渠道和表达 | 验收/继续条件 |
|---|---|---|---|

Reddit/HN 是反馈渠道之一。原调研的帖子样本互动有限，且本次检索不是全站随机样本，既不能预测爆发，也不能据此宣布这些渠道无效。现阶段更应问它们能否带来合适的任务与失败反馈。

**发布节奏：**先完成一个能复现的任务包，再决定是否制作下一篇；一次社区实验后先处理反馈、记录结果，再换角度或渠道。无需每周强行发产品贴。推广、商店提交、发帖和广告均是后续执行项，本轮没有执行这些动作。

## 7. 验证、指标与复盘

### 开发验证

修 F01 时把观察到的坏行为写成预期“不能发生”的常规回归测试；原 `privacy-evidence.audit.ts` 是历史缺陷存在证明，保留证据，不把其“通过”当修复通过。对应测试放入既有 settings/content/background/learn 测试范围，覆盖未同意、升级状态、跨表单、历史外发及明确清除。

功能提交按涉及范围执行必要检查：根目录 `npm run compile`、`npm test -- --run`、`npm run build`；代码风格检查 `npm run lint`。既有基线为 46 测试通过、Lint 0 错误/22 警告，不以旧基线代替新修改的验证。网站修改执行 `website` 下 `npm run typecheck` 与 `npm run build`，再检查相关断点、键盘操作和 Demo 异步行为。低风险文案不另写镜像测试。

浏览器审计可复用原脚本思路，但需先核对其中临时工具路径。上线前另查真实域名、状态码、可抓取正文和安装链路。一次本地 Lighthouse 分数不能作为线上 Core Web Vitals 成绩；对真实模型、控件和外部网页做明确版本的端到端验收。

### 最小指标表

| 层级 | 看什么 | 复盘节奏 / 边界 |
