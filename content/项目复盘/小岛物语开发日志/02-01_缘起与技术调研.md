# 01 缘起与技术调研

## 1.1 需求从哪来

项目起点是两个问题：

1. 有没有直接用 Unity、Godot 这类游戏引擎、让 LLM 来做游戏的好方案？
2. 有没有专门用来做游戏的 LLM？

调研之后，用户直接提出了开发需求：

> 你帮我用 Godot 命令行开发一款类似于动物森友会这样的游戏（不过是 2D 版），能够通过鼠标控制移动主角，然后 NPC 都有自己的话术内容。你需要自己下载 godot 然后自己安装配置，游戏素材你可以连接 107 服务器，使用文生图或者文生视频模型来进行，你也可以从网上检索获取。

紧接着又补了一条分工要求：具体实现交给 `codex-delegate`，Claude 负责策划、设计和测试验收。

所以这个项目同时是一次实验：**用两个 AI Agent 分工（一个当策划和验收、一个当程序），从零做出一个能玩的游戏。**

## 1.2 第一轮调研：用游戏引擎 + LLM 做游戏

资料来源是 Reddit（r/aigamedev、r/godot、r/gamedev、r/Unity3D 等）和网页搜索。

### 三类方案

| 路线 | 代表 | 适用场景 |
|---|---|---|
| A. 编码 Agent + 引擎命令行 | Godot 无界面（headless）运行、Unity 官方 Unity CLI | 社区主流；最快，也最省 token |
| B. 用 MCP 桥接编辑器 | Godot：godot-mcp、godot-ai、GodotIQ；Unity：CoplayDev/unity-mcp、IvanMurzak/Unity-MCP、Unity 官方 MCP（已改为付费） | 编辑器里的东西（预制体、序列化字段），以及运行时观察 |
| C. 引擎内置 AI | Unity AI、Ziva（Godot，商业）、Summer Engine | 不想折腾的人，但能控制的东西少 |

### 社区的几条共识

1. **Godot 最适合 AI 开发。** 场景（`.tscn`）、资源、脚本都是文本文件，Agent 可以直接写。
2. **大而全的 MCP 反而拖后腿。** 有人做过对照实验：同一个需求，用 godot-ai MCP 花了 27 分钟、11% 的周额度；不用 MCP、只用 Godot 命令行，3 分钟、2% 额度，画面还更好。原因是每个 MCP 工具的定义都常驻上下文，50 多个工具光定义就吃掉约 4 万 token。
3. **MCP 真正的价值是“让 AI 看见结果”。** 只做观察的轻量 MCP（日志、场景树、截图）有用；更简单的做法是让 Agent 在游戏里自建调试入口，用来跳到指定状态、截图、查节点。
4. **把引擎源码 clone 到本地给 Agent 查**，能减少它照着过时文档写错。
5. **成败取决于模型外面那套循环。** 一个 Godot 4.7 + Claude Code 做的仓储经营游戏（约 3.4 万行，已上 Steam 页面）的经验是：每次改动都要过语法检查和无界面模拟测试，Agent 还要自己打开游戏看效果，之后才算完成。AI 最弱的是审美。
6. 失败案例的高赞评论指出：你得知道游戏具体该怎么做，AI 才帮得上忙；而游戏架构恰恰是 AI 最容易搞砸的地方。

## 1.3 第二轮调研：有没有“游戏专用 LLM”

结论：**没有一个专门做游戏、而且比通用模型强的“游戏版 LLM”。** 为游戏专门训练的模型集中在世界模型、素材生成和 NPC 运行时这几类。

| 方向 | 现状 |
|---|---|
| 写游戏代码 | 通用前沿模型最好。唯一找到的“游戏代码专用模型”是一篇微调 LLaMA-3 写 Unity C# 的论文，4.8/5 对通用模型 4.7/5，差距在误差内。社区最常用 Opus 5.5，其次是 Codex |
| 游戏世界模型 | Genie 3、Matrix-Game 3.0、Hunyuan-GameCraft-2、Muse/WHAM 等，能按键鼠输入逐帧生成画面，但还停留在 demo 和原型阶段 |
| 素材生成 | 2D 有 FLUX.2 klein、Qwen-Image（都是 Apache-2.0）、PixelLab；3D 有 TRELLIS.2、Hunyuan3D 2.1、TripoSR |
| 游戏内 NPC | NVIDIA ACE + Nemotron-Mini 4B；社区更常用 Gemma 4 这类通用小模型加 RAG。值得记住的原则是：**LLM 只负责扮演 NPC，游戏状态和剧情由确定性的代码控制** |

## 1.4 调研怎样决定了技术路线

| 调研结论 | 本项目的做法 |
|---|---|
| Godot 文本格式对 AI 友好 | 选 Godot 4.7.2。主场景 `main.tscn` 只放一个根节点，世界全部由代码按 JSON 数据搭出来，Agent 只需要改 `.gd` 和 `.json` |
| 命令行优于大 MCP | 不装任何 Godot MCP。导入、冒烟、测试、截图全部走 Godot 命令行（`--headless --import`、`-s tests/run_tests.gd`、`--screenshot-test`） |
| 要让 AI 看见结果 | 游戏里自建截图模式 `--screenshot-test`：用真实注入的鼠标事件走完一套流程，每步截图。验收方每批亲眼看截图 |
| 外部循环决定成败 | 每批固定验收：导入 → 冒烟 → 测试 → 截图 → 人工看图 → 读 diff → 暂存。后来又加了变异测试来检验测试本身 |
| AI 最弱的是审美和架构 | 美术方向、选图、视觉问题判断都由策划方负责；架构在 `DESIGN.md` 里先定好，不让实现方自由发挥 |
| 素材模型选开放协议 | 静态素材用 Z-Image Turbo，走路帧用 FLUX.2 klein 4B，都跑在内网 107 服务器的 ComfyUI 上 |
| NPC 状态由代码控制 | 台词全部离线写好放在 `data/npcs.json`，好感度、每日限制、对话去重都是确定性逻辑；TTS 只负责“念出来” |

## 1.5 引擎的安装与环境

- Godot 4.7.2 stable 安装在 `%LOCALAPPDATA%\Programs\Godot\Godot_v4.7.2-stable_win64_console.exe`（用 console 版，命令行输出才能拿到）。
- Codex 的沙箱读不到这个安装目录，也写不了默认 AppData、读不了 Windows 根证书。所以 Codex 另写了两个工具：
  - `tools/fetch_godot.py`：从 Godot 官方 GitHub Release 下载同版本引擎，校验 SHA-256，放进 `.tools/`（约 499 MB，已 gitignore）。
  - `tools/run_godot.py`：只给子进程设置工作区内的 APPDATA / LOCALAPPDATA，用本机 certifi 的 CA 文件生成本地 `override.cfg`，并能把引擎输出记录到 `--record` 指定的日志。即使引擎退出码是 0，只要输出里有错误，也判定失败。
- 这样就有了两套运行环境：Codex 用隔离的 `.tools/` 副本，验收方用正式安装版。后来证明**两种环境都要跑测试**，因为 `user://` 指向的目录不同（见 [06 测试与验收](07-06_测试与验收.md#65-验收中发现的问题)）。
