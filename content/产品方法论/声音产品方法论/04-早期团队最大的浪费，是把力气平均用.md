# 早期团队最大的浪费，是把力气平均用

> 找到那个"不解决，其他全白干"的问题。

> **封面插图提示词**：一张"主要矛盾"主题插画。画面中有多个漂浮的问题标签：技术、用户、场景、商业化、增长、融资、组织；一束聚光灯只照在中央最大的标签"主要矛盾"上，团队成员把资源集中推向这个点。风格克制、有战略感，适合管理学长文，横版 16:9。

这是"产品判断链"系列的第 3 篇。上一篇做完现实诊断，团队手里有了一堆事实和假设。这一篇要解决的问题是：事这么多，先干哪一件？

这个问题看起来简单，但它恰恰是大多数早期团队栽跟头的地方。不是因为他们偷懒，而是因为他们太勤奋了——勤奋到把每一件事都当成头等大事来做。

## 现实诊断之后，问题反而更多了

这是很多团队没料到的：认真做完现实诊断，问题不是变少了，而是变多了。

技术还可以更好，界面还没设计，用户还没找到，融资材料还没写，市场策略没有，商业模式也不清楚。每个问题都重要，每个问题都有人盯着、都有人着急。诊断做得越认真，暴露出来的缺口就越多，团队反而更焦虑了。

于是团队进入一种"全都很忙"的状态：技术在调模型，产品在画原型，运营在找用户，创始人在见投资人。每个人都在加班，每个人都能在周会上报出一长串进展。看起来高效，但几个月过去，没有一个关键问题被真正打穿。

这种状态特别有迷惑性，因为它在每一个局部都说得通。技术觉得"模型效果再好一点，产品才有底气"；产品觉得"原型先画出来，才好跟用户聊"；运营觉得"用户得先攒一批，后面才好验证"；创始人觉得"投资人这边节奏不能断"。每个人都在做正确的事，每个人都有充分的理由。可是把这些"正确的事"加在一起，团队却始终没回答出那个最该回答的问题。

> **插图提示词**：四个人分别用力推着四个不同方向的箱子（技术、原型、用户、融资），每个人都满头大汗、姿态认真，但四股力量指向四方，中间那个真正该被推动的大石"主要矛盾"纹丝不动。强调"人人都很忙、力气却互相抵消"，克制的现代商业插画，灰白底、深蓝主色、橙色标注中央大石，16:9。

更隐蔽的代价是，这种忙碌会消耗团队的信心。三个月后回头看，大家会发现声音效果确实好了一点、原型确实漂亮了一点、用户名单确实长了一点，但"这个产品到底能不能成"这个根本问题，和三个月前一样模糊。力气花光了，焦虑还在，这才是真正让人泄气的地方。

早期团队最不能做的，恰恰就是这个——**平均用力**。

## 主要矛盾：决定阶段性质的那一个

这里要借用一个很朴素、但对产品极其有用的思想：在复杂事物里，要抓主要矛盾。

《矛盾论》里讲，任何复杂事物在发展过程中都存在很多矛盾，但其中总有一个是主要矛盾，它的存在和发展，规定或影响着其他矛盾的存在和发展。换句话说，主要矛盾决定了当前阶段的性质。产品也是一样：在任何一个阶段，决定团队该干什么、不该干什么的，都不是问题的数量，而是那一个起决定作用的矛盾。

所以，主要矛盾不是"唯一的问题"，而是那个决定当前阶段性质的问题。它的判断标准是这样一句话：

> 这个问题不解决，其他事情做得再好也没用；这个问题一旦解决，其他事情才有继续推进的意义。

注意这句话的两层含义。

第一层是"不解决就全白干"——它卡住了整个方向能不能成立。在它被解决之前，你在别处的所有投入都建立在一个未经验证的假设上，随时可能整体作废。比如方向探索期，"用户到底要不要这个东西"如果是错的，那你把界面打磨得再精致、把架构设计得再优雅，都是给一栋盖在沙地上的楼做精装修。

第二层是"解决了别的才有意义"——它一旦松动，后面一连串问题会跟着变容易，甚至有些问题会自动消失。一旦你确认了用户真实需要、并且知道他们要用来干什么，那么界面该怎么设计、功能该怎么排优先级、增长该往哪个人群投，这些原本悬而未决的问题，会突然有了判断的依据。主要矛盾就像一把钥匙，它打开的不是一扇门，而是后面一整排门。

> **插图提示词**：一把钥匙插进最前面一扇门的锁孔，随着它转动，身后一整排门依次被点亮、自动打开，门上分别标着"界面设计""功能优先级""增长投放""商业模式"。强调"解开主要矛盾这一把锁，后面一排门跟着开"，简洁概念插画，灰白底、深蓝主色、橙色高光打在钥匙和第一扇门上，16:9。

同时满足这两层，才是主要矛盾。只满足第一层、不满足第二层的，往往是"必要但不充分"的卡点——解决了它也带不动别的；只满足第二层、不满足第一层的，则常常是"锦上添花"的优化——做了会更好，但不做也死不了。其他问题不是不重要，而是**现在还不能抢走主要资源**。

## 全都很忙，却在用次要矛盾的活消耗主要矛盾的资源

平均用力最隐蔽的危害，不在于"没做主要矛盾"，而在于"用次要矛盾的活，悄悄消耗了本该投给主要矛盾的资源"。

资源是有限的。早期团队就那么几个人、那么几个月、那么点钱和注意力。注意力尤其稀缺——一个人同时盯五件事，每件事都只能分到两成的脑子，而真正难的问题，往往需要一个人把八成的脑子持续压在上面好几周才啃得动。当大家把精力平摊到所有问题上时，主要矛盾拿到的，恰恰是被切碎后剩下的那一小块。

举几个具体的例子，看看资源是怎么被次要矛盾偷走的：

- 技术同学花两周把声音生成的延迟从 800 毫秒优化到 500 毫秒。这是好事，但在"还不知道用户拿声音干什么"的阶段，这两周本可以用来跑通三个真实场景的端到端流程，看看用户到底卡在哪一步。延迟优化属于"产品方向定了之后再做也来得及"的事，提前做，就是借用了诊断阶段的资源。
- 产品同学把设置页做得特别完整，音色、语速、情绪、停顿、背景音全都能调，每个参数都有精美的滑块。可这个阶段的主要矛盾是"用户能不能在 10 秒内感知到声音差异",一个塞满参数的界面反而把这个感知点淹没了——用户进来先被一堆旋钮劝退，根本没听到那句"哇这声音不一样"。
- 创始人为了配合投资人"想看个东西"的要求，组织全员冲刺两周做了一个功能完整的 Demo。Demo 很惊艳，投资人也点头了，但团队为此推迟了用户访谈，结果拿了意向之后，依然不知道这个产品凭什么留住人。

这几件事的共同点是：每一件单独看都没错，甚至都挺漂亮。问题在于它们都消耗了同一池子的资源，而这个池子本该优先供给主要矛盾。次要矛盾的危险，从来不是它本身错了，而是它太合理、太顺手、太容易出成果，于是不知不觉就把团队最宝贵的注意力吸走了。

判断一件事是不是在"偷资源"，有个简单的问法：如果这件事现在完全不做，我们回答主要矛盾的速度会变慢吗？如果不会，那它就可以、也应该往后排。

## 声音 AI 团队的主要矛盾，不是"赶紧做 Demo"

回到声音 AI 团队。

他们一度以为，当前的主要矛盾是"我们得赶紧做一个 Demo 出来"。这个念头很有说服力：Demo 能给投资人看，能让团队有成就感，能证明技术行，还能在内部凝聚士气——大家盯着一个看得见的产物冲刺，总比对着一堆开放性问题干瞪眼舒服。

但仔细想想，Demo 真的是那个"不解决就全白干"的问题吗？

不是。用前面那两层含义去套一下就清楚了。第一层，"做不出 Demo"会卡住方向成立吗？不会——他们的技术已经能做出惊艳的 Demo 了，声音的拟真度、情绪、音色控制都拿得出手，Demo 这个东西他们随时能产出，它根本不是卡点。第二层，"做出 Demo"之后，别的问题会变容易吗？也不会——Demo 做出来，他们依然不知道该给谁用、用户会不会持续用、靠什么收钱。两层都不满足，Demo 自然不是主要矛盾。

真正卡住方向成立的，是另一组问题：

- 用户到底拿声音 AI 去完成什么任务？
- 他们靠声音赚钱吗？如果赚，是怎么赚的？
- 如果不赚钱，他们为什么会持续使用？
- 如果做陪伴，用户要的是一个 AI 助手，还是一个像真人一样、能接住情绪的短时陪伴对象？

这些问题不想清楚，Demo 做得再漂亮，也只是一次技术演示。它能赢得一句"哇好酷"，但赢不来一个能持续运转的产品。"哇好酷"是一次性的，看完就过去了；而产品要活下去，靠的是用户第二次、第十次、第一百次主动打开它的理由。这个理由，恰恰藏在上面那组问题的答案里。

而且，这组问题一旦有了答案，下游会瞬间清晰：知道了用户靠有声书分成赚钱，就该做长文批量生成而不是短句配音；知道了用户要的是被接住情绪而不是被解答问题，陪伴产品的表达方式就该往"短、口语、有语气词"调，而不是堆砌信息量。这正是主要矛盾的标志——它一旦松动，后面一连串决策都跟着有了方向。这部分该怎么具体验证，本系列后面讲"用户任务"和"MVP 验证"的两篇会展开。

所以这个团队的主要矛盾，不在"做不做得出来"，而在"用户拿它干什么、凭什么持续用"。在这个矛盾解决之前，投入大量工程去做完整产品，就是把力气用错了地方。

## 同一件事，这阶段是重点，下阶段是干扰

主要矛盾不是固定的。产品在不同阶段，主要矛盾会变，而且会"迁移"——它会从一个问题转移到下一个问题。更关键的是：同一件事，在这个阶段是必须集中力量解决的重点，到了另一个阶段，可能就变成了分散注意力的干扰。

| 阶段 | 主要矛盾可能是 | 不该过早投入 |
| --- | --- | --- |
| 方向探索 | 用户是否真实需要 | 完整系统开发 |
| 技术样板 | 用户能否感知差异 | 增长投放 |
| MVP 验证 | 用户能否完成真实任务 | 后台、权限、复杂配置 |
| 初期增长 | 是否有复用和传播理由 | 企业级能力 |
| 商业化 | 是否有稳定付费理由 | 单纯追求热度 |
| 规模化 | 质量、成本和组织稳定性 | 创始人手工兜底 |

看这张表的纵向，能更清楚地体会到"迁移"和"干扰"是怎么回事。

拿"增长投放"举例。在"初期增长"阶段，它是当之无愧的主要矛盾——产品已经被验证能用、用户能感知差异，这时候最该回答的就是"能不能复制、能不能传开"。可同样是投放，如果放在"技术样板"阶段去做，就成了不折不扣的干扰：产品差异点还没打磨到用户一听就懂，这时候花钱买来的用户进来一脸茫然，转头就走，钱烧了，还得出一个错误结论——"这产品没人要"。同一笔投放预算，时机对了是加速器，时机错了是毒药。

> **插图提示词**：同一个"投放"动作放在两条时间轴上的对比。上半部分时机正确：火箭加注燃料后稳稳升空；下半部分时机过早：同样的燃料浇在还没搭好的半截发射台上，烧成一团火、什么也没飞起来。强调"同一件事，时机对了是加速器，错了是毒药"，现代商业插画，灰白底、深蓝主色、橙色火焰，16:9。

再拿声音 AI 团队的"完整产品开发"举例。在方向探索期，埋头做完整产品是典型的力气用错地方；可一旦 MVP 验证通过、确认了用户真的愿意用，"把产品做扎实、做完整"就反过来变成了那个阶段的主要矛盾——这时候还停留在简陋原型上，反而会卡住增长。所以你会看到一个有意思的现象：团队在前一个阶段拼命克制自己别做的事，到了下一个阶段，恰恰是必须冲上去做的事。

这就引出了这张表背后真正的原则：**每个阶段，只允许有一个主要矛盾**。

不是说其他问题不管了，而是其他问题不能占用当前最多的资源。在"方向探索"阶段就去打磨 UI 精细度、追求技术架构的完美，本质上是用次要矛盾的活，消耗了主要矛盾的资源。而判断一件事现在到底是重点还是干扰，标准不在这件事本身好不好、该不该做，而在它和"当前这一个主要矛盾"的关系——是帮着把它打穿，还是把资源从它那里分走。

阶段切换的时机也值得团队定期复盘：主要矛盾是不是已经解决了？如果解决了，下一个主要矛盾是什么？这种"主要矛盾的交接"如果没有被显式地讨论和确认，团队很容易在一个矛盾已经解决之后，还惯性地把资源压在老问题上，迟迟不肯转向新的重点。

## 这和"好战略"是一回事

抓主要矛盾，听起来像个朴素的道理，但它其实和管理学里讲的"好战略"是同一件事。

好战略有一个被反复强调的结构（Richard Rumelt 在《好战略，坏战略》里讲得很清楚）：先**诊断**问题，再制定**指导方针**，最后形成**连贯的行动**。这三者是有顺序、且环环相扣的。

- **诊断**：当前真正卡住我们的，到底是什么？为什么这个市场现在有机会？这一步是在给问题定性，相当于抓主要矛盾。
- **指导方针**：基于诊断，我们选择从哪里切入、走哪条路、又明确不走哪条路。它是应对主要矛盾的总体思路。
- **连贯的行动**：资源、产品、技术、运营全都围绕这个切入口协同发力，而不是各干各的。

这三步里，诊断是地基。指导方针是从诊断里长出来的，连贯行动又是从指导方针里长出来的。地基错了，上面盖什么都是歪的。

很多团队没有战略，不是因为没有目标。恰恰相反，他们的目标特别大、特别多："今年要做出行业最好的声音产品""要拿下百万用户""要建立技术壁垒"。问题在于，他们跳过了诊断——

> 很多团队没有战略，不是因为没有目标，而是因为没有诊断。

目标喊得震天响，但没人说得清"当前真正卡住我们的，到底是什么"。这就是"有目标不等于有战略"的根源：目标只是你想去哪里，战略却是你对"此刻为什么去不了、最该先迈哪一步"的判断。少了诊断这一步，目标就是空中楼阁，它指明了方向，却没告诉任何人明天早上该先做什么。

缺了诊断的团队，通常有几个一眼可辨的特征：目标很多但没有取舍，什么都想要；口号很大但落不到具体问题上；每个人都很忙，但行动彼此不连贯——产品、融资、市场、研发各讲各的故事，拼不成一条线。这几个特征，声音 AI 团队前期几乎全中：又想做工具、又想做陪伴，又想要传播、又想要付费，投资人那边讲技术故事，产品这边画完整原型，谁也没先停下来问一句"我们现在最该回答的，到底是哪个问题"。

诊断错了，后面的指导方针和行动全都会错，而且是越努力错得越远——因为连贯的行动会把一个错误的诊断高效地放大。抓主要矛盾，本质上就是在做这个诊断，它是好战略的第一步，也是最容易被"我们很忙"的假象跳过的一步。

## 怎么判断哪个是主要矛盾

落到操作上，判断一个问题是不是当前的主要矛盾，可以问三个问题：

1. 这个问题不解决，会不会导致整个方向无法成立？
2. 这个问题解决后，其他问题是否会明显变得容易？
3. 这个问题是否应该占用当前最多的资源？

三个都是"是"，它大概率就是主要矛盾。前两个问题对应主要矛盾的两层含义，第三个问题则是在逼团队从"嘴上承认重要"走到"行动上真的倾斜资源"——很多团队卡就卡在第三问，嘴上都说用户场景最重要，可一看排期，工程师还是全扑在技术优化上。

如果想更系统一点，可以把候选矛盾列成一张表，逐个过：

| 候选矛盾 | 当前证据 | 如果不解决会怎样 | 是否主要矛盾 |
| --- | --- | --- | --- |
| 技术效果不够 | | 用户感知不到差异 | |
| 用户场景不清 | | 做出来没人知道怎么用 | |
| 商业路径不清 | | 有流量但无持续收入 | |
| 渠道触达困难 | | 产品好但找不到用户 | |
| 团队认知不一致 | | 反复换方向、重复开发 | |

填这张表有两个讲究。一是"当前证据"那一栏必须填真东西——是访谈记录、后台数据、还是某个真实用户说的话，而不是团队的猜测。没有证据支撑的判断，本质上还是在拍脑袋，只不过换了张表格的外壳。二是填的过程本身就是在逼团队对齐：当大家把各自心里默认的"主要矛盾"摊到同一张表上，往往会发现彼此根本不在同一个频道——技术觉得是效果，产品觉得是场景，创始人觉得是融资节奏。这张表的价值，一半在结论，一半在它逼出来的这场争论。

以声音 AI 团队为例，把表填完会发现：技术效果这一栏，证据是"Demo 已经能让人惊艳"，所以不解决也不至于全白干，它不是主要矛盾；而用户场景这一栏，证据是"团队说不清用户拿去干什么、靠什么持续用"，一旦不解决，后面所有投入都悬空——它两层含义全中，主要矛盾就此浮出水面。

## 小结

早期团队最大的浪费，不是做错了某个功能，而是把有限的力气平均摊在了所有问题上，结果哪个都没打穿。平均用力的可怕之处在于，它每一步都显得很合理、很勤奋，却在整体上让团队原地踏步。

抓主要矛盾，就是在做战略诊断：找到那个"不解决就全白干、一解决别的就变容易"的问题，然后把资源集中过去。每个阶段只盯一个，并且警惕那些用次要矛盾的活、悄悄偷走主要矛盾资源的"合理忙碌"。主要矛盾还会随阶段迁移，同一件事这阶段是重点、下阶段是干扰，团队要定期复盘它有没有变。

声音 AI 团队的主要矛盾，不是"做不做得出 Demo"，而是"用户拿声音干什么、凭什么持续用"。

但要回答"我们凭什么做这个"，就得先回到团队自己身上——我们真正的优势到底是什么？而且，优势的作用可能和你想的相反：它不是用来扩张的，是用来划边界的。
